# Move a node between documents

## WHAT

Add the ability to move a node, together with its subtree, to a different
location in the project. The destination may be in the same document or in
another document.

Requirements:

- Each eligible node's menu shall include a "Move" action.
- If the node or its subtree contains an inserted image, the Move action shall
  remain visible but disabled. Its tooltip shall explain that moving nodes
  with images is not supported yet. StrictDoc cannot yet recalculate a relative
  image path for a new document location. This restriction is temporary.
- If the node or its subtree contains an autogenerated node, the Move action
  shall remain visible but disabled. Its tooltip shall explain that moving
  autogenerated nodes is disabled. StrictDoc does not write autogenerated
  nodes back to an `.sdoc` file, so it cannot persist such a move.
- The Move action shall open a modal with the project's documents and
  all their nodes. The modal shall present them as a collapsible tree that
  follows the document structure and the existing TOC behavior.
- Each node row shall show the full node type in a badge.
- The tree shall include every node in document order and preserve the node
  hierarchy. It shall include titleless nodes such as TEXT.
- A node with a title shall use it as the row label. For a titleless node, the
  label shall use a preview of its main content field, limited to 80
  characters. If the node has no main content value, the label shall use the
  first non-technical field with a value in grammar order, then UID, then any
  remaining field with a value. An image-only field shall use the image file
  name. The node type shall provide the final fallback when no field has a
  value.
- The tree shall mark the branch being moved.
- The user shall be able to place the moved node before or after any eligible
  node in the tree, at any level.
- A document or composite node shall also accept the moved node as its last
  child. Empty documents and empty composite nodes shall provide this
  placement.
- Pointer input shall show the selected location with a TOC-style drop
  indicator.
- Selecting a location shall open a confirmation panel without contacting the
  server. The message shall name the destination document and describe the
  selected placement. For a node target, it shall also name the target node.
- Yes and Enter shall submit the move. Cancel and Escape shall close only the
  confirmation panel. They shall not submit the move. The move modal and its
  tree shall remain open and unchanged.
- The UI shall prevent placing a node inside itself or inside one of its
  descendants.
- For a cross-document move, the destination grammar shall represent every
  node in the moved subtree without changing it. The UI shall disable an
  incompatible document. The backend shall reject an incompatible request
  that bypasses the UI. Compatibility shall be based on the node types,
  fields, values, and relations present in the moved subtree, not on a literal
  comparison of the source and destination grammars. Differences that affect
  only unused grammar elements or fields shall not block the move. The same
  rule applies to an empty document with the standard grammar.
- After confirmation, the backend shall move the complete subtree to the
  selected location. It shall preserve node types, fields and their values,
  UID and MID fields, relations, and the internal parent-child structure. It
  shall not remove unsupported fields or convert the moved nodes.
- The picker may allow the user to select the node's current location. The
  server shall accept this as a no-op and show "The node is already at the
  selected location." in the modal. It shall not rewrite the document, update
  project content, or report a successful move.
- A successful move shall not close the modal. The document content behind the
  modal shall reload to show the result.
- After a cross-document move, the reloaded source document shall no longer
  contain the moved node. After a move within the same document, the reloaded
  document shall show the node in its new position.
- Reloading the document content shall preserve the content viewport in the
  same way as node deletion.
- After a successful move, the modal shall offer a link to the node's new
  location. The link shall open the destination document and scroll to the
  moved node.
- The user shall be able to close the modal with its close action or with
  Escape. Closing it shall not trigger another content update.

## WHY

Users currently cannot relocate a node once it exists in a document. As
project structure evolves, requirements and sections often need to move to
a different document, or to a different part of the same document, without
being deleted and manually recreated. This is only possible today through
manual editing of `.sdoc` files.

## HOW

The feature uses a project-wide recursive renderer, the existing backend
command, and a feature-local tree control. The renderer produces nested
`ul`/`li` elements with the same visual rhythm as the document TOC. It walks
every node in `section_contents`, so the rendered hierarchy matches the
document structure instead of the TOC subset. It does not reuse or change the
single-document TOC scripts.

`move_node_tree.js` initializes trees inserted through Turbo. It handles
branch collapse, pointer placement preview, confirmation, and submission to
the move endpoint. Pointer zones follow the existing TOC move behavior: the
upper half selects `before`; the lower half selects `after` or `child`
depending on horizontal indentation. A horizontal line previews the location.
A placement click stores the pending target on the client and opens a small
confirmation panel over the tree. The script sends the request only after the
user confirms it. Cancel and Escape discard the pending target and close this
panel without replacing the move modal. When represented in the placement
tree, the source branch remains visible and marked, but it is not draggable.

The template marks the elements and values used by the controller with
`data-js-move-node-tree-*` attributes. The script does not query presentation
classes or test hooks. End-to-end tests use stable `data-testid` hooks for
visible controls and results. They use the feature attributes only when they
check the tree's behavior or state.

Each node row uses the shared badge component to display the complete
`node_type`.

`get_move_node_tree_title()` supplies a label for every row. It uses `TITLE`
when available. For a titleless node, it first checks the grammar element's
`content_field`, then non-technical fields in grammar order, UID, and any
remaining fields. It normalizes field text to one line and limits content
previews to 80 characters. For a field that contains only an RST, Markdown, or
HTML image, it extracts the file name from the image path.

The backend accepts `before` and `after` relative to an existing node. It
also accepts `child` for a document or composite node and appends the moved
subtree to that container. This provides a destination for empty documents and
empty composite nodes. Backend validation rejects `child` for non-composite
nodes even if a request bypasses the UI. The regular picker does not offer a
`child` placement for these nodes. A forced request receives a 422 response,
and the modal shows: "A non-composite node cannot contain child nodes."

The placement tree does not block no-op locations. Before mutating the tree,
the backend detects whether `before` or `after` keeps the node next to the same
target, or whether `child` keeps it as the container's last child. For a no-op,
it returns a modal-only Turbo response without writing an `.sdoc` file,
updating `last_updated`, or reloading the document content.

Cross-document moves require the destination grammar to accept every node in
the moved subtree without changing its structure. The validation covers node
types, composite declarations, fields, choice values, required fields, and
relations. A document without an explicit `MID` field is incompatible with a
node that has one. The picker disables incompatible documents, and the backend
rejects requests that bypass the picker.

The tree only renders collapse controls when an item has child nodes. The
source document and the ancestors of the moved node start expanded; other
documents start collapsed. Bulk expand and collapse controls remain a possible
follow-up.

### Test coverage

Implemented under
`tests/end2end/screens/document/move_node_across_documents/`.

- `move_node_cross_document_happy_path` covers cross-document placement,
  disabled Move actions and image-specific tooltips for a node and its
  subtree, collapse controls, move confirmation through its buttons and
  keyboard controls, modal close, and the link to the new location.
- `move_node_within_same_document` covers reordering in one document.
- `move_node_viewport_preserved_on_close` covers viewport restoration.
- `move_node_subtree_moves_as_whole` covers subtree integrity, disabled
  targets inside the moved branch, and an unrelated valid target.
- `move_node_relations_preserved_cross_document` covers relations from both
  sides of a cross-document move.
- `move_node_into_empty_document` covers the `child` drop zones for an empty
  document and an empty composite node. It also verifies that these targets
  do not render collapse controls before receiving their first child. The
  same scenario forces `child` for a non-composite node and checks the 422
  message rendered in the modal.
- `move_node_from_enable_mid_to_default_grammar` covers blocking a move that
  would remove explicit `MID` fields from the moved subtree.
- `move_node_current_location_is_no_op` checks the full document structure in
  the move tree, including consecutive TEXT nodes, a nested TEXT node, and an
  image-only TEXT label. It also covers a TEXT node placed back at its current
  boundary and a node already at the last `child` position. The source files
  remain unchanged in the same server run.

Focused unit tests cover command validation and tree mutation, subtree checks
for images and autogenerated content, grammar compatibility, document
references, and the three no-op placements. The existing autogenerated
document E2E scenario also checks the disabled Move action and its tooltip.

### Deferred work

- Show node nesting in the document content view. It currently does not
  distinguish `Section + Text` from `Section > Text`, so moving a node into or
  out of a section can change the document structure without an obvious visual
  change. The move itself is correct; visualizing the resulting hierarchy is a
  separate task.
- Recalculate image paths so nodes containing images can move between
  documents.
- Add bulk expand and collapse controls to the placement tree.
- For an empty destination document, offer to copy the source grammar and
  related document settings before moving the first node. This must be an
  explicit user choice because it changes the destination document.
- Consider showing the moved branch as a compact tree fragment in the modal
  header.
